# Current test results

[User guide](../README.md) · [Technical guide](TECHNICAL.md) · [Detailed test log in Spanish](FEASIBILITY.md) · [Planned test cases in Spanish](TESTING.md)

Two physical Omarchy computers on one LAN paired using matching six digit codes on both machines. The receiver initially timed out because its firewall blocked the chosen TCP port; a rule scoped to its local interface, subnet, address and port allowed pairing. The user later confirmed that **Preview LAN rule** and **Authorize this rule** worked from the receiver panel.

The mouse crossed from the source's right edge to the receiver and returned across the receiver's left edge on two separate physical attempts. The user confirmed local mouse control after each return. A physical Escape press also returned control. These results used the same two computers and one monitor arrangement; the development log records the agent revisions and earlier failures.

With both agents updated to release 0.19.0, the source's physical **Super+V** opened the clipboard history on the receiver after a left-edge crossing. The user also confirmed that the pointer returned to the source. This verifies modifier delivery and return in that physical session; it does not establish that every shortcut or keyboard layout works.

During a later active-session plugin/shell reload, the receiver logged several authenticated connections that closed immediately. A new source process then established a stable session, and the user confirmed that crossing and return worked. The receiver logs rule out a blocked TCP port or failed pairing for those attempts. The prior source process did not retain its stderr, so the precise reason it closed is unconfirmed. The panel now shows the most recent retry error while reconnecting; stop active sessions before updating either plugin.

The same rapid authenticated disconnect recurred with 0.19.3 even without a plugin reload. On the receiver, the plain `failed to fill whole buffer` error matched the sequential read of the Wayland keymap file descriptor during virtual input setup. Release 0.19.4 reads that file at offset zero without changing the compositor's shared file position. With the corrected receiver and the previous source agent, a 25-second connection stayed ready with one authentication and no retry error; 20 consecutive local virtual input initializations also succeeded. After both computers were updated to 0.19.4, the user confirmed that **Connect** stayed at **Ready** for more than 20 seconds and that physical edge crossing and return both worked.

The original trapped cursor episode involved a source `connect` process in a suspended `T` state, which could not process Escape, return feedback or termination signals. A separate immediate recapture occurred after Escape; the current agent requires the returned pointer to move 96 pixels inside the source before rearming the capture edge. Hyprland's unlocked `solitaryBlockedBy: null` response is also handled when an active workspace is present.

On 0.19.7, pressing **Choose** for a file caused the Omarchy Quickshell process to abort. The coredump and journal place the abort in GLib/GVfs during the native GTK dialog, with a failed 4-byte allocation; no OOM kill was recorded. Version 0.19.8 forced Qt Quick's non-native file and folder dialogs, which opened in an isolated offscreen QML test but still crashed the live panel with SIGSEGV in GLib. In 0.19.9, the agent opens the desktop portal file chooser in a separate process. The user selected a file through the integrated panel button, saw its path, and confirmed Quickshell remained alive.

On 2026-10-02, the receiver listened on its LAN address at port `47833` but UFW blocked TCP connections from the paired Omarchy; remote control port `47832` was already open. After a LAN-scoped rule was applied to `47833`, the remote port became reachable. The user observed an image offer in the receiver panel. A separate harmless text file sent from the second physical Omarchy was offered, accepted, saved to a temporary folder, and acknowledged as delivered and verified by the sender. This validates one physical file transfer in this direction, including paired authentication and receiver consent. The file receiver handles one offer and then exits; another transfer requires **Wait for a file** again. Release 0.20.0 includes a dedicated file-port firewall action and a visible listening state. The dedicated action still needs a physical UI check.

On 2026-10-02, the `alpha` receiver was physically tested on **Windows 11 x64**. Windows and a previously paired Omarchy received the same IPv4 address from DHCP at different times. The Omarchy's pinned key stopped the first attempt with `PeerKeyChanged` before a source-side code appeared. The old key was stored outside the active peer store without revocation. The user then compared and approved a matching six-digit code on Windows and Omarchy. An authenticated latency probe completed 20 exchanges, and the UI-started connection stayed **Ready** for over 20 seconds. The user confirmed an Omarchy-to-Windows pointer crossing, edge return, a click, a harmless key press, and Escape return on a second crossing. Super+E on the physical Omarchy keyboard opened Windows File Explorer, and the user returned. The user tried several other key combinations; all worked, although their names were not recorded. A text file sent from the Omarchy panel was offered, accepted, and saved on Windows; the panel reported verified delivery. That session used an earlier build without clipboard synchronization. On 2026-10-03 the user confirmed text copied and pasted in both directions with the updated Windows agent. Two identities on one IP still require manual profiles or distinct addresses.

On 2026-10-03, Windows 11 x64 was also tested as the physical input source to an Omarchy receiver on the same LAN. The Windows console reported Ready, the Omarchy receiver recorded active control, and the user confirmed pointer movement, a click and a key on Omarchy. The user returned to Windows both by crossing the Omarchy entry edge and by pressing Escape on the physical Windows keyboard. The receiver subsequently released the active control state. The user also confirmed that pasting Windows clipboard text and the keyboard combinations tried with Windows/Super worked in this direction. This verifies one Windows-to-Omarchy pair and layout; the names of every combination were not recorded.

Local loopback and integrated tests cover pairing, Noise XX, discovery, simulated network address changes, file offer/acceptance, return messages, virtual input and capture. The [technical guide](TECHNICAL.md) lists the commands. The firewall helper has a test for rule scope and confirmation, and the setup scripts have tests that preserve identity and remove only tracked packages.

For 0.19.7, a local encrypted loopback test keeps two mesh links open, revokes an idle peer, verifies its socket closes while the other link remains usable, then revokes the active peer and verifies that the mesh loop receives the error that triggers capture release. The complete Rust test suite (72 tests) and Clippy passed locally. This does not replace a physical multi-computer mesh test.

The following still need physical verification: other keyboard shortcuts and layouts, wheel and dragging between the two Omarchy computers; file transfer in the reverse direction, larger files and interrupted transfers; multiple receiver mesh; other screen edges and monitor arrangements; locking, sleep and network loss. Windows still needs untested keys and layouts, wheel, drag, Windows→Omarchy files, lock, and other screen layouts.
